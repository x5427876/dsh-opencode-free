# Agent Note: 上游过载既不该画红，也不该换通道再问一次

Status: implemented

## Problem

上一条提交加了 `upstream-overloaded` 这个分类，**却没有把它接进两处该接的地方**，
于是它一落地就以错误的身份出现。2026-10-06 线上：

```
nemotron-3-ultra-free   红 失败   code=upstream-overloaded  http=200
```

两个错：

1. **画成红色「失败」**——红色说的是「这个模型不行」。而 503 是上游 Nvidia 的容量，
   与模型无关。标准 U1 把闸门拒绝／额度用尽／key 无效／超时／空回复都列为
   「不是模型退休的证据」，过载显然属于同一族。
2. **还会白问第二条通道**——`isCallerScoped` 没有它，于是扫描把上游的 503 当成
   「这条通道不行，换一条」，又花一次共享桶的请求买回同一个 503。

而加这个分类的目的正是「让面板能说出它是什么」——结果面板把它归进了最糟的一类。

## Decision

两处接线，外加一件顺带该做的：

1. **`isCallerScoped` 纳入 `upstream-overloaded`**：上游答 503 就会在另一条通道也答 503，
   再问一次是用共享桶买同一个答案。
2. **客户端 `CALLER_CODES` 纳入它**：行是灰点，不是红叉。
3. **灰色行的原因改为内联**：`未测到 · 额度用尽`、`未测到 · 匿名层被拒`、
   `未测到 · 上游过载`。此前三种完全不同的情况都只显示「未测到」三个字，
   具体原因藏在悬停提示里——扫一眼卡片的人拿不到原因（使用者在本次会话里问过两次
   「为什么」）。灰色语义不变：仍然不是模型的失败。

## Alternatives considered

- **不加入 `isCallerScoped`，让它继续换通道**——「万一另一条通道是好的呢」。
  但上游 503 是**容量**问题，与走哪条通道无关；ADR 早已用实测说明同一个模型在错误通道上
  会回「not supported for format」，那是**路由**问题，不是容量问题，两者不该混。
- **把它当作模型的失败（保持红色）**——红色读作「这个模型不行」，而 503 的含义恰恰相反；
  用户会因此去换一个完全可用的模型。
- **新增第四种颜色**——「未测到」已经是「我们没问到它」这一族的全部含义，
  再加一种只会让读的人多记一条规则。

## Consequences

- **收益**：过载第一次被当成它自己——面板说「上游过载（稍后重试）」而不是「失败」，
  而每次这样的失败**省下一次请求**。
- **代价与已知上限**：一条真正只在这一条通道上出现的过载不会再触发换通道。
  代价是那种模型要等下一轮（最多一天）才被重新问；收益是常态下省下一次请求。
  上游过载按定义就是全局的，所以这个取舍方向是对的。
- **UI**：灰色徽标现在有两段文字（「未测到 · 额度用尽」）。若空间不足，
  徽标本身是 `nowrap`，长文案可能溢出——需要在真实卡片上看一眼再定，这里不预设。

## Verification

- `GUARD: an overload costs one request, not one per channel`（传输层）：喂一个真实的
  503-overload 帧，断言 code 正确**且 `calls === 1`**（另一条通道没被问）。
  变异验证：把它移出 `isCallerScoped`，测试失败。
- 客户端改动由既有的渲染测试整体覆盖；`CALLER_CODES` 的成员变化不影响字典 parity。
- 其余 274 条测试通过。
